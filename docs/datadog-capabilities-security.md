# Native Python security lab

`//fixtures:datadog_security_suite` uses the existing Django rootfs and pinned Python SDK. It sends independent HTTP requests to first-party routes, then compares each returned SDK trace/span identity with the native intake root before examining security findings. The configured `DD_TRACE_HEADER_TAGS` creates the request ownership marker through Django instrumentation.

Source cases exercise query names/values, header names/values, cookie names/values, form bodies, paths and path parameters. Each has a bound-SQL safe control and an otherwise identical concatenated SQLite query. Assertions require the real vulnerability type, exact source origin and value, linked evidence part, first-party file location, pinned schema, and native stack linkage. They also validate the SQLite query span and Django parent graph. URI and multipart source-origin gaps remain explicit.

Sink cases execute actual subprocess argument handling, a local file read, arithmetic evaluation, a loopback HTTP call, harmless pickle data, header insertion, redirect creation, Django template escaping, weak hashing/randomness, and cookie security flags. Each tainted sink has an untainted control; strong hashing is the hash/random baseline. The header route follows the pinned upstream Django workload's documented direct header-store access.

The lab retains original native intake records, HTTP responses, exact executed app/view source, control captures and their hashes. MessagePack security metadata remains raw byte arrays in those captures. The assertion decoder independently validates the [pinned upstream IAST schema](https://github.com/DataDog/system-tests/blob/098fe0967c587db8a16b74a1e711777d0a9d5867/tests/appsec/iast/vulnerability_schema.json).

The bulk source/sink profile uses the existing stress sink with a 64 MiB capture budget to retain its combined binary reports. Other security profiles use the normal 4 MiB sink. Binary backing allocations and wire-type provenance count toward these budgets; production decoder regressions enforce the normal limits independently.

The Python SDK's v0.5 encoder omits structured security reports despite enabled native AppSec/IAST instrumentation. Those cases are unsupported on that wire and do not satisfy the runtime gate. Real user-event and client-IP/fingerprint assertions can still pass. The SDK reports harmless pickle input as `UNTRUSTED_SERIALIZATION`, a name absent from the pinned schema enum; its sink assertion examines the real structured report but does not claim pinned-schema validation. Redirect reports have a one-line stack/location discrepancy, retained as an unsupported assertion; their genuine sink findings do not establish extended-location/stack parity.

To let the SDK's normal first-party location classifier recognize Bazel workloads, the probe copies the exact source files into the retained output directory and starts the application there. It does not override SDK location, taint or vulnerability-reporting internals.

The `waf-controls` profile loads a retained local libddwaf rule configuration and exercises matching, no-match, rule exclusion and HTTP block actions. It preserves native rule identifiers, matching addresses/values, configuration version and load diagnostics, response bodies and blocked-request tags. This profile demonstrates local configuration behavior; remote configuration requires separate protocol tests.

The `rasp-controls` profile uses the [pinned upstream nonblocking rules](https://github.com/DataDog/system-tests/blob/098fe0967c587db8a16b74a1e711777d0a9d5867/tests/appsec/rasp/rasp_non_blocking_ruleset.json). Actual local file, loopback HTTP, SQLite, subprocess and fixed harmless shell operations must produce detector findings with exact input addresses, root-span identity, detector metrics and linked exploit stacks. Independent uncorrelated operations provide safe controls.

The `api-enabled` and `api-disabled` profiles execute the same typed JSON and authentication workloads. Assertions inspect compressed request/response schemas, query/header/path types, JWT structure and cookie names while rejecting raw secret values. Captured SDK telemetry independently proves endpoint registration, activation origin, WAF initialization and request counts. The telemetry relay preserves actual SDK request bodies and forwards native traces to the intake sink; it does not simulate SDK telemetry.

The `appsec-standalone` and `iast-standalone` profiles disable APM tracing and require genuine security findings, `_dd.apm.enabled=0` on every span in the corresponding trace, security trace-source metadata and keep priority. The Python manifest marks collection of all custom request/response headers as missing; the header workload retains that unsupported outcome. Standalone structured findings remain unsupported on v0.5. User-blocking response IDs, URI/multipart taint origins and the other SDK discrepancies described above remain gaps rather than passing assertions.
